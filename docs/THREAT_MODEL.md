# Threat model — Phase 6

Written before implementing Phase 6 controls. This is an engineering threat model, not a penetration test or regulatory assessment. Source-derived statistics and learned weights remain sensitive even when no source rows are displayed.

Trust boundaries: browser → API/session; external OIDC issuer → validated identity; authenticated membership → organization-scoped database queries; API/worker → private storage; PostgreSQL queue → supervised computation. Database administrators, identity-provider administrators and storage administrators remain privileged infrastructure actors. Worker processes are trusted service processes, not browser identities.

| Asset | Threat | Existing control | Planned Phase 6 control | Remaining risk |
| --- | --- | --- | --- | --- |
| Source clinical datasets | Cross-tenant access, UUID swapping, malicious upload | Bounded CSV, generated keys, no row previews, hashes | Organization membership, scoped queries, editor upload permission | Authorized users and infrastructure administrators can mishandle data; CSV parsers need maintenance |
| Synthetic datasets | Broken object authorization, tampered bytes | Registered artifact IDs and SHA-256 | Membership checked before controlled retrieval; private S3-compatible store | Synthetic data can disclose source information; SHA-256 is not encryption |
| Trained synthesis models | Unsafe deserialization, model extraction | No arbitrary model upload; downloads restricted; trusted internal loading | Preserve restrictions and enforce tenant relationship invariants in workers | Reviewed internal libraries still deserialize trusted model artifacts |
| Evaluation/governance reports | Report injection, ID guessing, public URLs | HTML escaping, CSP, artifact registration | Authenticated tenant-scoped downloads and actor audits | Aggregate statistics/column names may be sensitive; downloaded copies leave platform control |
| Release policies | Privilege escalation, unauthorized changes | Immutable hashed versions | Owner-only creation, same-project/organization references | Organization thresholds are operational criteria, not universal privacy standards |
| Audit records | Editing/deletion, sensitive log exposure | PostgreSQL append-only trigger, no row values | User/org/request correlation; preserve system/worker actors | Database superusers can bypass protections; no tamper-proof claim |
| User identities/sessions | Stolen sessions, CSRF, token leakage | None | OIDC code flow + PKCE/state/nonce validation; opaque server sessions; HttpOnly/Secure production cookies; CSRF token + origin checks | XSS can act with a browser session; identity-provider compromise and endpoint-device compromise remain |
| Tenant/project metadata | SQL injection, stale organization state, privilege escalation | Parameterized SQL, bounded inventories | Persist issuer+subject identity, explicit organization membership and roles, scope every product query, clear browser context on switching | Application isolation requires regression tests for new endpoints; no RLS claim |
| Storage credentials | Secret leakage, path traversal | Canonical local key checks, ignored environment files | Environment/credential-provider injection, generated object keys, no permanent public URLs | Operator configuration and provider permissions remain critical |
| Database credentials | Credential leakage, connection exhaustion | Hidden SQL parameters, bounded pool/timeouts | Strict production configuration, non-root containers, backup/restore runbook | Privileged database access and uncoordinated backups remain risks |
| OIDC credentials | Secret leakage, malicious issuer/redirect | None | Fixed configured issuer/client/callback, maintained OIDC library, no tokens in logs/localStorage | Provider outages prevent new logins; configuration must match deployment |
| All stored data | Deleted-data resurrection | Manual reconciliation only | Explicit retention semantics, authorized deletion request, background logical object deletion, retained audit tombstones | Backups and object-store versions can retain bytes; restore must reconcile deletion history |
| Jobs/artifacts | Worker spoofing, cross-project publication, crash/retry races | SKIP LOCKED, session ownership, lease/token fencing, compensation | Trusted ownership snapshot and relationship verification; preserve existing concurrency checks | A compromised worker/database administrator remains privileged; database/storage are not one atomic transaction |
| Browser/API | XSS, misconfigured CORS, callback abuse | React escaping, safe errors, request size bounds | Explicit credentialed CORS, security headers, production HTTPS, proxy rate limits | Targeted automated checks do not establish complete security |

Implementation and actual verification evidence are recorded in PHASE_6_VERIFICATION.md; unverified release checks and remaining scanner findings must not be treated as passed. No anonymity, clinical validity, HIPAA/GDPR compliance, secure physical erasure or zero-risk guarantee follows.
